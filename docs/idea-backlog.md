## 1. 목표와 설계 관점

**구축 방향 (2026-10-30 변경): DeepSeek Harness(DSH)의 Agent 루프·플러그인·세션·도구 계약 등 설계 원리를 참고하고, 하네스는 LangChain/LangGraph로 직접 구현한다.** DSH는 참고 자료이며 실행 기준선으로 운영하지 않는다. 세부 계약과 DSH에서 가져올 원리의 범위는 설계 과정에서 결정한다.

MVP의 업무 범위는 **사용자 검토 기준에 따른 문서 검토**(근거 탐색·비교·대조·판정)다. 데이터 조정·변환·수정과 문서·표·차트 생성은 추후 도구로 추가하는 것을 계획하되, 구현 여부는 MVP 이후 결정한다. **사용자 질의를 먼저 확인하고 정해진 작업 Tool로 라우팅한 뒤, 해당 Tool 내부의 고정 워크플로를 실행하고 결과를 반환한다.** 기존 RAG·문서 처리 단계는 Tool 내부에서 재사용하는 모듈이나 하위 워크플로로 두며, 수정·생성 Tool을 나중에 붙일 수 있도록 경계를 열어 둔다.

문서 파싱, VLM 보완, 청킹·색인, 검색, 근거 조회, 수치 계산, 검토, 인용 검증을 독립 모듈로 분리한다. 각 모듈 종료 시 **입력·출력·실행 상태와 버전 정보**를 보존해, 특정 단계만 교체하거나 동일한 중간 결과에서 후속 단계를 재실행할 수 있도록 한다.

문서 준비와 아티팩트 의존 관계에는 **데이터플로 그래프(DAG), 체크포인트, 증분 재실행**을 활용할 수 있다. **MVP에서 업무 Tool의 실행 순서는 사전 정의된 그래프와 제한된 조건부 분기로 제어한다.** 공통 실행 생명주기·취소·재개는 하네스가 담당하며, Agent가 자율적으로 재계획하거나 Tool을 연쇄 호출하는 구조는 MVP 이후 별도 실험 대상으로 남긴다.

핵심 목표:
- 모듈별 책임·입출력 계약의 명확화 및 팀원 작업의 독립성 확보
- 실패 위치와 원인 추적, 중단 시 복구, 실행 제약의 일관된 적용
- 공통 입력에서 검색·검토·검증 전략을 교체하는 비교 가능 환경 구성
- 불필요한 파싱·임베딩·모델 호출을 피할 수 있는 단계별 결과 재사용
- 문서에 근거한 판단을 해당 문서 버전과 원문 위치에 연결하여 재현성 보존
- (추후 수정·생성 도구 도입 시) 입력, 적용한 변환, 산출물 버전과 변경 이력을 추적
- 로컬 모델을 기본으로 실행하고, 외부 모델 사용은 실험 구성으로 격리

## 2. 기술 구성 후보

| 구성 요소 | 제안 역할 | 참고 및 유의점 |
|---|---|---|
| LangGraph | **하네스 구현 기반(결정).** 상태 그래프, 분기·합류, 체크포인트, 중단·재개, 실행 제어 | Agent 실행과 문서 처리 등 하위 워크플로를 구성. 세부 그래프 구조는 설계에서 결정 |
| LangChain | **하네스 구현 기반(결정).** LLM·임베딩·Retriever·도구 어댑터 | LangGraph 노드 내부와 Agent 구현에서 사용. 중복 실행 계층을 만들지 않음 |
| DSH (DeepSeek Harness) | **설계 참고.** Agent 루프, 플러그인·서비스 경계, 세션·도구 이벤트, 실행 정책 | 실행 기준선으로 운영하지 않음. 참고한 원리와 LangGraph 구현으로 옮긴 방식을 기록 |
| 모델 실행 | **로컬 모델 기본(결정)**, Ollama Cloud 오픈 웨이트 모델은 실험용 | 실험용 클라우드 모델에는 외부 전송이 허용된 자료만 사용. 연결 방식·모델 선정은 설계에서 결정 |
| Open Notebook | LangGraph 활용, FastAPI와 비동기 워커 분리, 로컬 데이터 관리 | 서비스 통합 구조를 참고하되 저장소·워커 선택은 독립적으로 결정 |
| 로컬 영속 저장소 | 그래프 체크포인트, 실행 메타데이터, 아티팩트 저장 | 체크포인트와 아티팩트를 논리적으로 분리하고 실제 저장 기술은 추후 결정 |

사용자 요청의 **작업 Tool 라우팅**과 **Tool 내부 고정 워크플로**를 분리한다. 하네스는 세션, 도구 실행, 작업 상태, 예산, 복구와 관찰을 위한 공통 인터페이스를 LangChain/LangGraph 위에 제공한다. RAG 검색 내부의 공통 흐름은 **Dense + BM25 + RRF**, 추가 후보 재평가는 **교체 가능한 선택형 Reranker**로 분리한다([파이프라인 설계](document-pipeline.md)). 검색의 기본 구성은 비교 실험으로 결정한다.

## 3. 모듈 경계와 저장 지점

아래 문서 준비·검토 흐름은 기존 RAG 업무의 구성 예시다. 범용 Agent의 모든 작업이 이 순서를 따르도록 고정하지 않으며, 수정·생성 능력의 공통 경계는 H-13에서 함께 검토한다.

### 3.1 문서 준비 흐름

**문서 등록/버전 식별 → 파싱 → (필요 영역 VLM 보완) → 문서·표 구조화 → 청킹 → 색인**

| 경계 | 저장할 대표 아티팩트 | 재사용·검증 관점 |
|---|---|---|
| 원문 등록 | DocumentVersion, 원문 해시·형식·위치 | 동일 원문 식별, 버전 변경 추적 |
| 파싱 완료 | ParsedDocument, 표·문단의 원문 위치 | 파서 변경 전후 출력 비교 |
| 구조화/VLM 보완 완료 | TableIR, 추출기 출처·검증 상태 | 원문 레이아웃·표 구성 및 위치 보존 |
| 청킹 완료 | ChunkSet, 청크 ID·원문/구조 참조 | 청킹 전략 비교 |
| 색인 완료 | IndexManifest, 임베딩 모델·설정·청크 집합 버전 | 불필요한 재색인 방지 |

### 3.2 질의·문서 검토 흐름

**질문 및 검토 기준 → 검색/리랭킹 → 근거 보강 및 도구 실행 → 검토 초안 → 주장·인용 검증 → 결과/판단 보류**

| 경계 | 저장할 대표 아티팩트 | 재사용·검증 관점 |
|---|---|---|
| 요청 분석 | ReviewRequest, 검토 기준·문서 범위 | 동일 조건으로 전략 변경 |
| 검색 완료 | EvidenceBundle, 문서·표·청크·근거 위치 | 검색/리랭킹 비교, 원문 조회 |
| 도구 실행 완료 | ToolResult, 수치 계산 입력·단위·출처 | 결정적 계산 재검증 |
| 초안 생성 완료 | ReviewDraft, 모델·프롬프트·참조 근거 | 재생성 없이 검증 로직 비교 |
| 인용 검증 완료 | VerificationReport, 불일치·미확인·판단 근거 | 검증 규칙 변경에 따른 결과 비교 |
| 최종 처리 | FinalReview, 성공/보완/판단 보류 상태 | 사용자에게 결과와 근거 제공 |

대용량 원문·이미지·표는 그래프 상태에 복사하지 않고, 안정적인 아티팩트 참조(ID/버전)를 전달하는 방식을 우선 고려한다. 문서 처리와 질의 처리는 서로 다른 그래프 또는 하위 그래프가 될 수 있다.

| H-12 | 쿼리 증폭·재작성(보류 아이디어) | 원본 질의 대비 Multi-query Generation, Query Rewriting, PRF, HyDE, Query Decomposition 등을 **선택형 검색 전처리·재검색 전략**으로 비교. 검색 품질(Recall@k·nDCG@k), 추가 호출·지연·비용과 질의 의미 왜곡 위험 검증 후 도입 여부 결정. 현재 기본 파이프라인에는 미포함 | 후순위 |
| H-13 | DSH 참고 LangChain/LangGraph 하네스 | DSH의 Agent 루프·플러그인·세션·도구 계약을 참고해 LangChain/LangGraph로 하네스를 직접 구현. MVP는 검토 작업, 수정·생성은 추후 선택 확장 | 높음 |

H-13의 **DSH 설계 참고 → LangChain/LangGraph 직접 구현**과 **검토 중심 MVP**는 결정된 방향이다(0절). 항목별 세부 구현 범위·우선도·기술 선택은 제안이며, 팀 데이터 계약과 사용 사례 및 실험 결과에 따라 확정한다.

**H-12 검토 조건:** 원본 사용자 질의는 수정하지 않고 보존하며, 생성·재작성된 질의와 방법·모델·설정 버전을 별도로 추적한다. PRF는 초기 검색 결과를 이용한 재검색 방식으로 RRF(순위 통합)와 구별한다. Query Decomposition은 Agent의 복합 질문 계획과 경계가 겹칠 수 있으므로 책임을 정한 후 검토한다. 현재 설계·코드에 모듈을 추가하지 않는다.

### 4.1 H-13 — DSH를 참고한 LangChain/LangGraph 하네스

**목적:** DSH의 설계 원리를 참고해 ReportAnchor에 필요한 실행 계약과 운영 특성을 정하고, LangChain/LangGraph 위에 하네스를 직접 구현한다. DSH는 실행 기준선이 아니라 설계 참고 자료다.

| 구분 | 백로그에 남길 작업 | 산출물 |
|---|---|---|
| DSH 원리 정리 | Agent 반복 실행, 컨텍스트 구성, 도구 계약, 플러그인 수명주기, 이벤트·세션 보존, 실행 정책과 복구를 문서·코드로 확인 | 참고할 원리, 가져오지 않을 부분과 그 이유 |
| LangGraph 대응 설계 | 정리한 원리를 LangGraph의 상태·노드·체크포인트·인터럽트, LangChain의 모델·도구 인터페이스에 대응 | 하네스 구조와 모듈 계약, LangGraph로 해결되지 않아 직접 구현할 부분 |
| 하네스 구현 (검토 MVP) | 검토 작업을 실행할 수 있는 범위부터 구현하고, 수정·생성 도구를 나중에 연결할 수 있는 경계를 유지 | 실행 가능한 하네스, 실행 기록, 검토 작업 결과 |

표는 구축 방향을 나타내며, 각 작업의 순서·병행 범위·완료 조건은 추후 설계한다. DSH 내부 구조의 일대일 복제를 전제하지 않는다. **2026-10-31 결정:** MVP에는 자율적인 Agent Tool 연쇄 호출 대신 **입력 확인·라우팅 → 목적별 Tool 고정 워크플로 → 결과 제공**을 사용한다([상세 구조](query-agent-mvp.md)).

**수정·생성까지 포함한 공통 설계 대상 (MVP 이후, 도입 시 검토):**

- **작업과 실행:** 목표·제약·완료 조건, Agent의 행동 선택, 관찰 반영과 재계획, 사용자 입력 대기·취소·재개. 실행 상태와 업무 판단 결과를 구분한다.
- **능력 구성:** 검색·원문 조회·계산에 데이터 정제·변환·수정 및 문서·표·차트 생성·편집을 연결한다. RAG는 선택 가능한 능력이며, 도구 조합과 실행 순서는 작업에 따라 달라질 수 있다.
- **작업 공간과 변경:** 원본·작업 중 데이터·생성 산출물의 식별자와 버전, 입력·변환·출력 계보, 변경 차이, 적용 상태, 충돌과 중복 적용 방지, 되돌리기 범위를 정의한다. 세션·체크포인트 복구와 실제 데이터 변경 취소를 별도로 다룬다.
- **작업별 검증:** 탐색·비교는 근거 정합성, 데이터 조정은 스키마·합계·제약, 생성·편집은 요구 내용·형식·렌더링 등을 확인하는 검증 모듈을 검토한다. 원문 사실과 생성한 제안·가정은 구별해 기록한다.
- **공통 출력 계약:** 작업 상태·산출물 참조·버전·오류 등의 공통 정보를 정의하고, EvidenceBundle·FinalReview 같은 업무별 결과는 해당 모듈의 출력으로 연결한다. 생성·수정 결과도 같은 실행·추적 체계에서 다룬다.

**실험·결정할 사항:**

- DSH에서 참고할 원리·계약의 범위와 LangGraph 구성 요소로의 대응 방식.
- LangGraph 최상위 Agent 그래프와 문서 처리 등 하위 워크플로의 책임 경계, 체크포인트·아티팩트 저장 기술.
- 로컬 모델 연결 방식과 모델 선정, Ollama Cloud 실험 구성의 격리 방법.
- 검토 작업의 사례·평가 기준과 하네스 기능·복구 동작의 수용 기준. 수정·생성 작업의 사례·평가 기준은 해당 도구 도입 시 정한다.

## 5. 저장 계층의 책임 구분

1. **Checkpoint**: 현재 Agent 또는 워크플로 실행 상태와 재개 지점. 실패 복구와 실행 제어를 위한 정보.
2. **Artifact**: 각 모듈의 입력·출력 및 근거를 버전과 함께 보존한 재사용 가능한 결과.
3. **Execution Trace**: 실제 호출 순서, 오류, 소요 시간, 비용 등 관찰·평가 가능한 실행 기록.

세 계층은 목적이 다르므로 동일 데이터로 취급하지 않는다. 체크포인트 복구가 곧 과거 모델 응답의 결정적 재현을 의미하지 않으며, 재실행 과정에서 외부 도구의 부작용이 중복되지 않도록 멱등성도 고려해야 한다.

권장 메타데이터 후보:
- 실행 계보: run_id, parent_run_id, node_id, attempt, input_artifact_ids, output_artifact_ids
- 자료 버전: document_id, document_hash, schema_version, source_locator, source_version
- 실행 조건: module_version, config_hash, model_id/parameters, prompt_hash, index_version
- 상태 및 지표: status, started_at, elapsed_ms, token_usage, retry_count, error_type
- 검증: evidence_refs, verification_status, evaluator_version, evaluation_set_version

캐시 적중 여부와 아티팩트 재사용 여부는 별도 지표로 기록한다. LLM 출력 캐싱은 동일 입력·모델 조건일 때만 허용하며, 비결정적 호출의 재사용 결과를 새로운 독립 모델 실행으로 간주하지 않는다.

## 6. 검증 및 비교 관점

하네스 자체의 품질은 최종 답변 점수와 별도로 측정한다.

- **운영·복구:** 완료율, 단계별 실패율, 재개 성공 여부, 중복 부작용 여부
- **성능:** 모듈별 시간, 전체 지연, 모델 호출 횟수·토큰, 캐시 적중·재사용률
- **재현성:** 원문/아티팩트/설정 해시 기록 충실도, 동일 조건 비교 가능 여부
- **문서 품질과 분리된 결과:** 검색 적중·원문 근거 정합성·표 구조 정확도·인용 검증 결과를 각 담당 평가 모듈에서 수신
- **수정·생성 작업:** 변경 적용 정확성, 산출물 요구 충족, 변경 계보, 중단 후 중복 적용 여부와 복구 가능 범위를 업무별 평가 모듈에서 수신

비교 시 문서·검토 기준·평가셋·모델/프롬프트 버전 및 캐시 상태를 통제한다. 총정답 수가 같더라도 문항별 회귀·개선을 분리하고, 평가셋과 원문이 충돌하면 지표 해석에서 해당 사실을 표시한다.

## 7. 외부 API 베이스라인과 자료 독립성

**기존 외부 API 기반 RAG는 비교용 레퍼런스로만 보존한다.** 관련 원본 코드·평가 기록은 [별도 레퍼런스 색인](../references/README.md)을 통해 확인하되, 신규 하네스의 기본 의존성에 포함하지 않는다.

- 참조할 것은 **문제 유형과 설계 교훈**(원문 위치 보존, 단계별 추적, 파싱·검색·검증 간 계약, 평가 결과 분리)이다. 특정 데이터셋의 파서·프롬프트·질문 라우팅을 그대로 이식하지 않는다.
- 파싱·청킹·검색·검증 모듈의 이름, 경로, 기본 설정에 **기관명·자료명·문서 제목·고정 파일 개수·파일명 접두사·특정 평가셋**을 포함하지 않는다.
- 기존 베이스라인에서 사용하는 외부 모델·임베딩 공급자는 **비교 환경에만 속한다.** 로컬 하네스 실행에 필수로 만들지 않는다.
- 공통 IR과 EvidenceBundle은 입력 자료의 의미가 아니라 **범용 구조·원문 위치·검증 상태·버전**을 표현한다. 도메인별 필드는 필요 시 선택적 확장으로 격리한다.
- 모델·파서·색인·평가셋이 달라질 때 결과가 부당하게 재사용되지 않도록 **입력 콘텐츠 해시와 설정/스키마/모듈 버전**을 확인한다.
- 레퍼런스 기반 측정치는 독립적인 일반화 성능이나 새 구현의 성능 보증으로 취급하지 않는다. 새로운 문서군에서도 구조·오류·근거 추적의 일관성을 확인할 수 있도록 평가 계약을 별도로 만든다.
- 단순히 기존 파서의 출력 형태와 일치한다는 이유만으로 이를 새 프로젝트의 표준 계약으로 확정하지 않는다. 공통 계약을 먼저 정의하고, 필요하다면 레퍼런스는 **별도 비교 어댑터**로 연결한다.

문서 파싱 단계의 구체적인 범용 모듈 경계와 데이터 의존 방지 원칙은 [독립 파싱 단계 설계](parsing-stage.md)에 정리한다.

## 8. 팀 내 논의·결정 필요 사항

1. 파서/VLM → RAG → Agent/검증 간 필수 필드와 스키마 버전
2. 상태 체크포인트와 대용량 아티팩트의 저장 기술 및 보존 정책
3. 캐시 무효화 기준(원문 변경, 파서/청킹 변경, 모델·프롬프트 변경)
4. 분기 실행 시 원문·평가 조건 고정, LLM 출력 재사용과 실제 재호출의 구분
5. 실패 유형, 재시도·중단 조건, 멱등성 및 개인정보·민감 문서 로그 정책
6. 기존 외부 API 베이스라인과 신규 하네스를 어떻게 격리하고 비교 인터페이스만 연결할지
7. DSH에서 참고할 원리·계약의 범위와 LangGraph 구현으로의 대응
8. (수정·생성 도구 도입 시) 작업 공간, 변경 적용·버전·복구 계약과 업무별 완료 조건
9. 로컬 모델 연결 방식·모델 선정과 Ollama Cloud 실험용 자료 범위
